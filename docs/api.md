# API endpoints — full notes

Moved out of CLAUDE.md on 2026-10-12.

## API

- [api/airtable.js](api/airtable.js) — proxy for Airtable requests (holds the PAT server-side)
  - **Read hardening (2026-10-01)** — the proxy is open to the internet, and three real leaks were found and closed: (1) **Tengiliðir** (all customer names/emails/phones) was readable → removed from `ALLOWED_FIELDS` (the planner only creates contacts); (2) **Tækifæri**'s "Fullt nafn 👤"/"Netfang 📧"/"☎️ Símanúmer" were in the public set → moved to `VERK_ONLY_FIELDS` (needs `?k=VERK_KEY`; kitchen-planner-review.html forwards its own `&k=`); (3) `REQUIRE_FILTER` was bypassable with `filterByFormula=TRUE()` → **every employee's PIN** was listable. Now `STRICT_FILTERS` only accepts the exact query shape each page sends (Starfsmenn: `AND({PIN 🔢}=<digits>,{Er starfandi? ✅}=1)`, Fjarvistir: must start `AND({Starfsmaður}="…",`), "PIN 🔢" is never returned, and `WRITE_ONLY` (Vefspjall, Skipulag villur) refuses GET. Also: an all-zero PIN equals a BLANK PIN in an Airtable formula, so "0000" could log in as an active employee with no PIN set — refused in the proxy, `/api/eigandi-clock` and `/api/isak-todo`. **When adding a table/field to `ALLOWED_FIELDS`, assume anyone on the internet can list it.**
  - **`/crm` contacts + self-serve product/material creation (2026-10-18)** — scoped after a dedicated round of questions with the user (contacts cover customers AND suppliers; Útfærslur only ASSEMBLE from existing Vörulisti parts, never a new Vörulisti row, never the "Skipulag →" planner-integration fields; new material lines are descriptive-only, no purchase cost/time). Four tables opened up for the first time: **Fyrirtæki 🏢** (`tbl2akoCETBx9S1SK`, companies — also the Birgjar/supplier table Vörulisti/Efnislisti link through and Pantaðir listar's supplier-email automation reads), and widened access on **Tengiliðir**, **Útfærslur**, **Efnislisti**. All four got a new Airtable field **"Óyfirfarið — Rakel ⚠️"** (checkbox), forced `true` on every create via `FORCED_CREATE_FIELDS` — same self-approval-proofing pattern as `Sjálfsafgreiðsla — óyfirfarið ⚠️` elsewhere; cleared by an owner directly in Airtable, no in-app review screen by design. Editing an *existing* record (not creating) is NOT flagged — it takes effect immediately.
  - **New: `PATCH_REQUIRES_KEY`** (alongside the pre-existing `CREATE_REQUIRES_KEY`) — every pre-2026-10-18 `WRITABLE_FIELDS` table relied on the field allowlist alone as its PATCH boundary (the record id is the "secret"), fine for e.g. Tækifæri pipeline fields. The four tables above now carry PII (kennitala, address, phone) or pricing-adjacent structure that didn't exist behind this proxy before, so PATCH on them additionally requires `?k=VERK_KEY`, same gate POST already had.
  - **Real latent bug found and fixed in the same pass**: `tblQ8zeUanriESWvL` (Tengiliðir) had been in `REQUIRE_FILTER` since the "+ Nýtt verkefni" contact search shipped (2026-10-18) but had no matching `STRICT_FILTERS` entry — exactly the `filterByFormula=TRUE()` gap the 2026-10-01 round closed for Starfsmenn, just reopened for a different table the same day it was introduced. Fixed by adding a `STRICT_FILTERS` regex matching the exact `OR(SEARCH(...),SEARCH(...),SEARCH(...))` shape both the old search and the new contacts page send.
  - **A second latent bug, introduced by the fix above and caught the same day**: the GET handler's old `STRICT_FILTERS[tableId] && (recordId || !test(...))` check blocked fetching ANY record by id on a table that merely has a `STRICT_FILTERS` entry — fine for Starfsmenn/Fjarvistir (by design, PIN-filter is the only intended way in), but it silently 403'd crm.html's and skrifstofa.html's job-popup contact resolution the moment they tried `GET tblQ8zeUanriESWvL/<id>` or `GET tbl2akoCETBx9S1SK/<id>`, since those two got a `STRICT_FILTERS` entry too (for the TRUE() fix above) without needing the by-id block. Split into two separate concerns: `BLOCK_RECORD_ID` (Starfsmenn, Fjarvistir only) explicitly refuses by-id reads; `STRICT_FILTERS` now only gates *list* queries (`!recordId && …`). A record id is a 17-char random string, not realistically guessable, so allowing by-id reads through `STRICT_FILTERS` tables that don't also opt into `BLOCK_RECORD_ID` isn't a regression.
  - **`api/starfsmenn-overview.js`** (2026-10-18) — the Eigandi-only Starfsmenn table on skrifstofa.html's Yfirlit (live hours/sick-days-this-month via Starfsmenn's own pre-built rollups, clocked-in status via a `{Út}=BLANK()` Stimplanir query, and — only here, never through the general proxy — `Kaup per klst 💲`). Never trusts the client's own claimed role: `api/skrifstofa-login.js`'s token changed from a per-day HMAC shared by every login that day to a **per-employee, per-day** HMAC (`skrifstofa-emp:<recordId>:<date>`), and this endpoint re-fetches that specific employee's `Tegund starfsmanns 🧑‍💻` fresh from Airtable on every call before returning anything — same "never trust a cached role" posture as `api/eigandi-clock.js`'s existing owner check, which this reuses the literal `"Eigandi 👨🏻‍💼"` string from.
  - Tækifæri (`tbl4LMXlQjp66RFKI`) `VERK_ONLY_FIELDS` gained `"Tengiliður verkefnis 👤"` and `"Teikningar úr skipuleggjara 📐"` (2026-10-18) — the job-detail popup's contact + self-serve-planner-drawings sections.
  - **VAT schedule, corrected** (2026-10-18, same day) — the first version assumed a clean "5th of every other month" rule; the user then posted RSK's real due-date table, which showed it's actually ~2 months after each period ends, bumped a day or two on weekends (7. apríl not 5., 7. desember not 5.) — a bank-holiday-aware "next business day" rule that can't be reliably reverse-engineered from 6 examples. `VAT_DUE_DATES` in skrifstofa.html is now the literal due-date list from that table (extend by hand once a year); `PAYDAY_SCHEDULE` (last calendar day of each month) was correct as originally built.
  - **`?k=VERK_KEY` bootstrap bug, found and fixed** (2026-10-18) — `K_STORE` (the office pages' shared localStorage key for VERK_KEY) had no path to get populated except a `?k=` query param somewhere in a URL the person happened to click; a fresh device/profile, a cleared browser, or a plain `/skrifstofa` bookmark never got one, so every VERK_ONLY_FIELDS read silently fell back to the public (often empty) field set and every VERK_KEY-gated write 403'd outright. Symptom reported by the user: contact search always showing "(ónefnt)", "+ Nýtt verkefni" → "Teikna í hönnuði" doing nothing. Fixed by having `/api/skrifstofa-login` hand back `verkKey` on a successful PIN login (the person already proved themselves staff) and having skrifstofa.html persist it into `K_STORE` — removes the bootstrap gap for every future login, not just a one-time patch.
- [api/field-check.js](api/field-check.js) — **daily field check (2026-10-06)**, Vercel Cron 06:40 UTC (`CRON_SECRET`), or by hand `GET /api/field-check?k=<VERK_KEY>` (read-only). It checks that every Airtable field name in `fieldDeps()` of api/airtable.js (allowlists + forced + filter-formula fields) and api/kp-submit.js still exists, using one GET per table with `fields[]` = all names: Airtable answers `UNKNOWN_FIELD_NAME` for each bad one in turn, so the token needs no schema scope. Anything missing → one row in **Skipulag villur 🐞** (Tegund "Airtable reitur") + `console.error`. Why: a renamed field used to fail silently (the proxy drops unknown read fields, writes 422). It does not cover field names that pages put into their own `filterByFormula`.
- **Rate limits (2026-10-06)** — Vercel Firewall (project firewall config, not in the repo; edit in Vercel → Firewall or `vercel api /v1/security/firewall/config`), per IP, 60 s fixed window: `/api/airtable` GET 240/min (label printing polls ~120/min, and the whole shop shares one IP), non-GET 60/min, `/api/kp-submit|kp-drawings` 10/min. Over the limit → 429. If a shop page starts getting 429s, raise the limit there first.

### Design: per-device floor tokens (replace the hardcoded VERK_KEY constant) — NOT built yet

**Today.** The same VERK_KEY is a string constant in app.html, cutlist.html, fraesing.html, labels.html, grain.html (and cnc.html as a default for `?k=`), and rides in `?k=` on every QR label URL (api/v.js → /velja). Anyone who views source or photographs a label owns the key. Endpoints that accept it (`k` query/body, plain string compare with `process.env.VERK_KEY`): `api/airtable.js` (VERK_ONLY_FIELDS reads, CREATE_REQUIRES_KEY, PATCH_REQUIRES_KEY, Tækifæri non-date fields, KEYED_STRICT_FILTERS), sala, virkni, verk-status, konto-vat, greidslur, pontun-print, tilbod-print, tilbod-pdf (HMAC with it), kp-pro, kp-price, kp-drawings (pro replace), kp-studio, kp-workdraw, smida-eydublad, staff-new-project, field-check and morgunyfirlit (manual dry run), v.js (injects it into the /velja redirect), skrifstofa-login (hands it back after PIN login). The floor only *needs* a subset: airtable.js (Eyðublað/Sögunarlisti/Efnislisti reads+writes, Quick Fix, Tækifæri reads), virkni, verk-status, v.js/velja.

**Proposal.**
1. *Endpoint* `POST /api/floor-token` (new, api/floor-token.js). Body `{ deviceSecret }` where deviceSecret is the existing kiosk pairing secret (`KIOSK_DEVICE_SECRET`, already stored in the shop tablets' localStorage by the `/klukka ?setup=` link) or a new one-time `?floor-setup=` link per phone. Returns `{ token, exp }`.
2. *Token* = `exp.deviceId.hmac` where hmac = HMAC-SHA256(`FLOOR_TOKEN_SECRET`, `floor:` + deviceId + `:` + exp). Stateless, no DB. Expiry 12 h for tablets (silently re-fetched on 401), 24 h for phones.
3. *Pairing.* Owner opens a one-time `/app?pair=<code>` link (code = HMAC of deviceId, shown in /eigandi); the page POSTs it once, stores `deviceSecret` in localStorage (same pattern as the kiosk). Revoke = bump `FLOOR_TOKEN_SECRET` or add the deviceId to a `FLOOR_REVOKED` env list.
4. *Verification.* New shared `api/_auth.js`: `checkKey(req)` accepts either `VERK_KEY` (office, unchanged) or a valid floor token, using `crypto.timingSafeEqual`. A floor token is accepted only by the floor subset above (airtable.js with a `floor` flag that does NOT unlock VERK_ONLY contact/PII fields, sala, konto-*, greidslur), so a leaked tablet token cannot read kennitölur or invoices.
5. *Pages send* `?k=<token>` exactly where they send the constant today (pages keep one `fetch` wrapper that re-pairs on 401). api/v.js stops injecting VERK_KEY and instead redirects with a 10-minute piece-scoped token (`HMAC(secret,'piece:'+pieceId+':'+exp)`) that only /velja and the Sögunarlisti PATCH for that piece accept.
6. *Rollout.* Ship `_auth.js` accepting both; move pages one by one; finally rotate VERK_KEY in Vercel (needs the owner) and delete the constants. Add a test that no html file contains the key shape.
